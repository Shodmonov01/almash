# Техническое задание

## Проект: платформа обмена игрушками и аксессуарами

### 1. Общая концепция

Платформа предназначена для пользователей, которые хотят **обменивать игрушки и детские аксессуары исключительно на другие игрушки и аксессуары**.

Основной принцип:

> **Никаких продаж, покупок, денежных переводов и внутренних платежей. Только обмен.**

Пользователь размещает предметы, которые готов обменять, указывает желаемые предметы и получает предложения от других пользователей.

Обмен может происходить в форматах:

1. **1 → 1**
2. **1 → несколько**
3. **несколько → 1**
4. **несколько → несколько**
5. **обмен набора на набор**
6. **цепочка обменов**, когда два пользователя не имеют прямого взаимного интереса, но могут быть связаны через других пользователей.

Пример:

> Пользователь A предлагает:
>
> * LEGO-машинку
> * набор фигурок
>
> Пользователь B предлагает:
>
> * большой набор LEGO

Обмен:

**2 игрушки A → 1 игрушка B**

Количество предметов само по себе не определяет ценность обмена. Пользователи самостоятельно договариваются о составе сделки.

---

# 2. Цели проекта

### Основная цель

Создать безопасную платформу, на которой пользователь сможет:

* разместить игрушку или аксессуар;
* найти подходящие предметы;
* предложить обмен;
* получить предложение обмена;
* договориться об условиях;
* безопасно совершить обмен;
* оставить отзыв после завершения сделки.

### Главные принципы

* нет денег внутри платформы;
* нет продаж;
* нет покупки;
* нет аукционов;
* нет денежных ставок;
* нет возможности требовать денежную доплату;
* каждая сделка должна иметь зафиксированные условия;
* система должна минимизировать мошенничество;
* спорные сделки должны иметь механизм разрешения;
* история всех действий пользователя должна сохраняться.

Пользователь может размещать:

### Игрушки

* конструкторы;
* машинки;
* куклы;
* мягкие игрушки;
* фигурки;
* настольные игры;
* пазлы;
* роботы;
* игрушечное оружие;
* радиоуправляемые игрушки;
* развивающие игрушки;
* наборы.

### Аксессуары

* детские рюкзаки;
* игровые аксессуары;
* аксессуары для кукол;
* аксессуары для конструкторов;
* игровые коврики;
* домики;
* гаражи;
* фигурки-дополнения;
* комплектующие.

Для каждой категории должен существовать собственный набор дополнительных характеристик.

---

# 4. Создание объявления

Пользователь нажимает:

**«Добавить предмет»**

Форма:

### Основные данные

* название;
* категория;
* подкатегория;
* описание;
* фотографии;
* видео;
* бренд;
* модель;
* примерный возраст;
* состояние;
* комплектация;
* наличие повреждений;
* отсутствие элементов;
* оригинал / неоригинал;
* размер;
* цвет.

### Состояние

Предусмотреть фиксированные значения:

* новое;
* как новое;
* хорошее;
* есть следы использования;
* требует восстановления;
* неполный комплект.

Пользователь обязан указать все существенные дефекты.

### Фото

Минимум:

**2 фотографии**

Для некоторых категорий может быть обязательным:

**3–5 фотографий.**

Фото должны показывать:

* общий вид;
* дефекты;
* комплектность;
* маркировку/модель;
* крупные планы спорных мест.

### Видео

Опционально.

Для дорогих/сложных игрушек рекомендуется видео.

---

# 5. Запрет скрытых дефектов

При создании объявления пользователь должен подтвердить:

> «Я указал все известные мне существенные дефекты и несоответствия предмета описанию.»

При наличии скрытого дефекта, обнаруженного после обмена, другая сторона получает возможность открыть спор.

Повторное нарушение снижает рейтинг пользователя и может привести к блокировке.

---

# 6. Что пользователь хочет получить

У каждого объявления должно быть два блока:

### Отдаю

Список предметов пользователя.

### Хочу получить

Пользователь может указать:

* конкретную игрушку;
* категорию;
* бренд;
* набор;
* несколько допустимых категорий;
* «рассмотрю любые предложения».

Пример:

**Отдаю:**

LEGO Technic + 3 фигурки

**Хочу:**

LEGO City / LEGO Technic / машинки / конструкторы.

---

# 7. Несколько предметов в одном обмене

Это обязательная функциональность.

Один пользователь может предложить:

### Вариант A

1 игрушка → 1 игрушка

### Вариант B

3 игрушки → 1 игрушка

### Вариант C

1 игрушка → 4 игрушки

### Вариант D

5 игрушек → 3 игрушки.

Сделка считается одной транзакцией, внутри которой находятся несколько предметов с каждой стороны.

---

# 8. Обмен наборами

Пользователь может создать собственный набор.

Например:

### Набор №1

* машинка;
* фигурка;
* гараж;
* аксессуары.

И обменивать весь набор целиком.

Также должно быть разрешено выбрать только некоторые предметы набора.

---

# 9. Поиск

Поиск должен работать по:

* названию;
* категории;
* подкатегории;
* бренду;
* возрасту;
* состоянию;
* расстоянию;
* типу предмета;
* набору;
* тегам.

---

# 10. Геолокация

Для каждого объявления:

* страна;
* город;
* район;
* примерный радиус.

**Точный адрес не показывается публично.**

До подтверждения сделки пользователи видят только:

> Ташкент, Юнусабад

После согласования обмена стороны самостоятельно выбирают место встречи.

---

# 11. Безопасные места для передачи

Система должна рекомендовать:

* людные общественные места;
* торговые центры;
* кафе;
* игровые центры;
* другие безопасные точки.

Запрещено показывать точный домашний адрес другого пользователя.

Для детей сделки должны проводиться только взрослыми представителями.

---

# 12. Создание предложения обмена

На карточке предмета:

**«Предложить обмен»**

Пользователь выбирает свои предметы.

Например:

> Я предлагаю:
>
> * LEGO City
> * машинку
> * фигурку

Взамен хочу получить:

> * набор LEGO пользователя.

После отправки создаётся предложение.

---

# 13. Переговоры

У каждого предложения есть отдельный чат.

В чате участники могут:

* обсуждать состояние;
* отправлять фотографии;
* отправлять видео;
* изменить состав обмена;
* согласовать место передачи;
* согласовать дату;
* подтвердить сделку.

Однако любые изменения состава обмена должны проходить **только через интерфейс сделки**, а не считаться подтверждёнными только из текста чата.

---

# 14. Фиксация условий сделки

После согласования формируется:

## Договор обмена

Например:

### Пользователь A передает

1. LEGO City
2. машинку Hot Wheels
3. фигурку

### Пользователь B передает

1. набор LEGO Technic

### Условие

Обмен производится одновременно.

После нажатия:

**«Подтвердить условия»**

состав сделки блокируется.

Любое изменение создаёт новую версию сделки.

---

# 15. Статусы сделки

Использовать следующие статусы:

1. `DRAFT`
2. `OFFER_SENT`
3. `NEGOTIATION`
4. `TERMS_AGREED`
5. `MEETING_SCHEDULED`
6. `HANDOFF_PENDING`
7. `PARTY_A_CONFIRMED`
8. `PARTY_B_CONFIRMED`
9. `COMPLETED`
10. `DISPUTED`
11. `CANCELLED`
12. `BLOCKED`
13. `EXPIRED`

---

# 16. Безопасное завершение обмена

Самая важная часть системы.

После встречи каждый участник должен подтвердить:

> «Я получил все предметы, указанные в сделке.»

Подтверждение производится:

### Вариант 1 — QR-код

У первого участника появляется QR-код сделки.

Второй сканирует его.

После сканирования оба получают:

> «Обмен подтверждён обеими сторонами».

### Вариант 2 — код сделки

Каждому участнику выдаётся одноразовый код.

Например:

`8492`

Код необходимо ввести после фактической передачи.

---

# 17. Защита от схемы «я нажал подтвердить, а товар не получил»

Нельзя автоматически завершать сделку по одному подтверждению.

Требуется подтверждение **обоих пользователей**.

Если:

A подтвердил

B не подтвердил

→ сделка остаётся в статусе:

`HANDOFF_PENDING`

Через определённое время пользователь получает напоминание.

---

# 18. Защита от мошенничества «подменил предмет»

До сделки сохраняются:

* фотографии;
* видео;
* описание;
* состояние;
* комплектация;
* серийные номера, если есть;
* дата публикации;
* изменения объявления.

После начала сделки исходное состояние объявления фиксируется.

Пользователь не может задним числом поменять фотографии или описание так, чтобы изменить доказательства.

---

# 19. Защита от мошенничества «товар оказался не таким»

При создании сделки обе стороны должны подтвердить:

> «Я ознакомился с фотографиями и описанием предмета другой стороны».

Если предмет существенно отличается от зафиксированного состояния, можно создать спор.

---

# 20. Система споров

Кнопка:

**«Открыть спор»**

Причины:

* предмет не передан;
* передан другой предмет;
* отсутствует часть комплекта;
* скрытый дефект;
* состояние существенно хуже описанного;
* пользователь исчез;
* пользователь отменил обмен после передачи;
* попытка мошенничества;
* нарушение договорённостей;
* подозрение на подделку;
* другое.

---

# 21. Доказательства по спору

Участники могут предоставить:

* фото;
* видео;
* переписку;
* фотографии до передачи;
* фотографии после передачи;
* QR/код сделки;
* время подтверждения;
* место встречи;
* историю изменения сделки.

Все эти данные должны быть связаны с конкретной сделкой.

---

# 22. Арбитраж

На этапе MVP:

**администратор платформы**

рассматривает спор вручную.

Позже возможно создание:

**системы автоматического risk scoring + ручной арбитраж.**

Администратор может:

* закрыть спор в пользу A;
* закрыть спор в пользу B;
* вернуть сделку в переговоры;
* заблокировать пользователя;
* установить предупреждение;
* отменить сделку.

---

# 23. Критически важный момент

Платформа **не должна хранить физические предметы**.

То есть не создаётся ситуация:

> «Отправьте игрушку нам, а мы передадим её другому».

На MVP это сильно усложняет проект.

Платформа является:

**сервисом поиска, согласования и фиксации обмена.**

Физическая передача осуществляется пользователями.

---

# 24. Курьерская доставка

Можно предусмотреть как отдельный этап.

Но:

### Деньги не должны проходить через платформу.

Приложение не принимает:

* оплату;
* комиссию;
* стоимость игрушки;
* денежную доплату.

Если в будущем появится доставка через стороннюю службу, она должна быть вынесена в отдельный сервисный контур.

---

# 25. Важный запрет — денежная доплата

В системе запрещено:

> «Я дам тебе игрушку + 50 000 сум».

Также запрещено:

> «Обменяю только если доплатишь».

Запрещено публиковать:

* цену;
* стоимость;
* денежную оценку;
* минимальную сумму доплаты;
* реквизиты для оплаты;
* номер карты с целью оплаты.

При обнаружении:

**автоматическое предупреждение + возможность блокировки.**

---

# 26. Контроль чата

Необходимо автоматически обнаруживать:

* суммы;
* валюты;
* номера банковских карт;
* кошельки;
* криптоадреса;
* слова «доплата»;
* «переведи»;
* «скинь деньги»;
* «оплата»;
* «заплати»;
* ссылки на платежные системы.

При обнаружении:

> «Внутри платформы запрещены денежные расчёты.»

При повторных нарушениях — ограничение аккаунта.

---

# 27. Telegram / внешний контакт

На первом этапе желательно запрещать передачу:

* телефона;
* банковских реквизитов;
* платёжных ссылок;
* подозрительных внешних ссылок.

При этом после создания подтверждённой сделки можно разрешить обмен минимальными контактными данными для встречи.

Все действия должны логироваться.

---

# 28. Защита от фейковых аккаунтов

Пользователь должен иметь профиль:

* имя;
* фотография;
* дата регистрации;
* количество завершённых обменов;
* процент успешно завершённых обменов;
* рейтинг;
* отзывы;
* количество отмен;
* количество споров;
* процент выигранных/проигранных споров.

---

# 29. Уровни доверия

Пример:

### Новый

0 обменов.

### Проверенный

5+ завершённых обменов.

### Надёжный

20+ обменов и высокий процент успешных сделок.

### Trusted

100+ обменов + высокий рейтинг + низкое количество споров.

Статус нельзя купить.

---

# 30. Репутация

После каждой успешной сделки:

1–5 звёзд.

Дополнительно:

* предмет соответствовал описанию;
* человек приехал вовремя;
* описание было честным;
* комплектность совпала;
* обмен прошёл без проблем.

---

# 31. Защита от накрутки рейтинга

Не разрешать:

* отзывы без завершённой сделки;
* несколько отзывов за одну сделку;
* повторные сделки между теми же пользователями для искусственного поднятия рейтинга;
* массовые однотипные аккаунты;
* взаимную накрутку.

Каждый отзыв должен быть связан с конкретной сделкой.

---

# 32. Защита от мультиаккаунтов

Для аккаунта сохранять технические признаки:

* Telegram ID / ID аккаунта;
* устройство;
* IP;
* поведенческие признаки;
* частоту создания объявлений;
* частоту отмен;
* подозрительные совпадения.

Важно:

**не блокировать пользователя только по одному техническому признаку.**

Решение должно приниматься по совокупности сигналов.

---

# 33. Антифрод-система

Для каждой сделки рассчитывается условный:

**Risk Score**

Учитываются:

* новый аккаунт;
* большое количество объявлений;
* массовая отмена;
* много жалоб;
* частые споры;
* одинаковые фотографии;
* одинаковые описания;
* подозрительные сообщения;
* большое количество аккаунтов с одного устройства;
* резкое изменение поведения;
* попытки перевести общение за пределы платформы;
* попытки обсуждения денег.

При высоком риске:

* дополнительные проверки;
* ограничение создания новых сделок;
* ручная модерация;
* временная блокировка.

---

# 34. Запрещённые предметы

Платформа должна запрещать:

* оружие;
* боеприпасы;
* наркотические/запрещённые вещества;
* опасные химикаты;
* поддельные товары;
* ворованные вещи;
* интимные товары;
* опасные предметы;
* товары, запрещённые законодательством конкретной страны;
* предметы с потенциальным риском для детей.

Список категорий должен настраиваться через админку.

---

# 35. Модерация объявлений

Объявление проходит:

### Автоматическую проверку

AI/антифрод проверяет:

* текст;
* изображения;
* запрещённые категории;
* признаки продажи;
* деньги;
* подозрительные слова.

### При подозрении

`PENDING_MODERATION`

Модератор принимает решение.

---

# 36. Защита фотографий

Фотографии объявлений должны содержать:

* watermark платформы;
* ID объявления.

Это не предотвращает копирование полностью, но позволяет обнаруживать повторное использование фотографий.

---

# 37. Защита от схемы «украл фотографию»

Если один и тот же предмет размещён несколькими аккаунтами:

* сравнение изображений;
* поиск похожих фотографий;
* сигнал модератору.

Особенно высокий риск:

> новый аккаунт + дорогой/редкий предмет + чужие фотографии.

---

# 38. Защита от схемы «сначала отправь мне»

Очень важно:

пользователь не должен рекомендовать другой стороне:

> «Сначала отправь игрушку, потом я отправлю свою».

Внутри платформы рекомендуемый сценарий:

### Одновременная передача

Обе стороны подтверждают передачу.

Если лично:

> одновременно передали → оба проверили → оба подтвердили.

---

# 39. Отмена сделки

### 8. Неявка

### 11. Социальная инженерия

# 63. Принцип «без денег» должен быть техническим

Важно не просто написать в правилах:

> «У нас нет денег».

Нужно сделать так, чтобы архитектура приложения **вообще не предполагала денежную сторону сделки**.

В сущности `Trade` не должно быть:

* price;
* amount;
* currency;
* payment;
* commission.

У сделки есть только:

**Items A ↔ Items B**

То есть математически модель:

`[A1, A2, A3] ⇄ [B1, B2]`

И всё.

# 65. Основная бизнес-модель

Так как пользователь хочет полностью исключить деньги из **самого обмена**, монетизацию можно рассматривать отдельно и не включать в MVP.

Например, в будущем:

* реклама;
* партнёрские предложения;
* платные дополнительные функции платформы.

> **сама сделка всегда остаётся бесплатным обменом вещей.**

3. добавить несколько предметов;
